# `Claim/$request-preauthorization`

## Purpose

Submits a Kenya SHA pre-authorization request for a Claim. This is identical to
`$submit-national-claim` except that `Claim.use` is overridden to `"preauthorization"` before
the FHIR bundle is built, signalling to SHA that the submission requests prior-approval rather
than a reimbursement claim.

Pre-authorization results are persisted to the Claim under a distinct extension URL so they
do not overwrite the claim submission snapshot.

## HTTP request

```
POST /fhir/R4/Claim/{id}/$request-preauthorization
POST /fhir/R4/Claim/$request-preauthorization
```

The instance form (with `{id}`) is the expected path. The type-level form accepts a
`claim` reference in the request body.

## Input parameters

| Name    | Type      | Required | Description |
|---------|-----------|----------|-------------|
| `claim` | Reference | no       | Only used when calling at type level — reference to the Claim to pre-authorize. Not needed for instance calls. |

## Output parameters

| Name                      | Type    | Description |
|---------------------------|---------|-------------|
| `status`                  | code    | `prepared` (no credentials) \| `submitted` \| `error` |
| `correlationId`           | string  | UUID for this pre-authorization request |
| `message`                 | string  | Human-readable outcome |
| `nextState`               | string  | Suggested next state label |
| `countryPack`             | string  | `kenya` |
| `shaClaimsEnvironment`    | string  | `uat` or `production` |
| `submissionEndpoint`      | string  | SHA endpoint used |
| `statusTrackingEndpoint`  | string  | SHA status-check endpoint |
| `responseStatusCode`      | integer | HTTP status code from SHA |
| `bundleId`                | string  | UUID that SHA uses to track this submission |
| `bundleEntryCount`        | integer | Number of resources in the submitted bundle |
| `rawBundle`               | string  | JSON representation of the submitted FHIR bundle |
| `rawResponse`             | string  | Raw SHA response body |
| `task`                    | Reference | Reference to the created Task |

## How it differs from `$submit-national-claim`

| Aspect | `$submit-national-claim` | `$request-preauthorization` |
|--------|--------------------------|------------------------------|
| `Claim.use` in bundle | `claim` | `preauthorization` |
| Extension URL on Claim | `https://afiax.africa/fhir/StructureDefinition/kenya-sha-claim-submission` | `https://afiax.africa/fhir/StructureDefinition/kenya-sha-preauthorization` |
| Task code | `submit-national-claim` | `request-preauthorization` |
| SHA endpoint | `POST /v1/shr-med/bundle` | Same |
| ClaimResponse created | Yes (via `$check-national-claim-status`) | No — awaits separate status check |

## SHA API call

```
POST {shaBaseUrl}/v1/shr-med/bundle
Authorization: Bearer <sha-token>
Content-Type: application/json

{FHIR Bundle with Claim.use="preauthorization"}
```

The SHA `bundleId` is generated by this operation (UUID), embedded in the bundle, and stored
in the extension on the Claim. Use it to track the pre-authorization request with SHA.

## Persistence

For each call, the operation writes:

1. **Task** (status `completed` or `failed`):
   - `code.text = "request-preauthorization"`
   - `businessStatus.text` = outcome status
   - `identifier[system='https://afiax.africa/identifier/correlation-id']` = correlationId
   - `output[]` includes bundleId, submissionEndpoint, statusTrackingEndpoint, responseStatusCode

2. **Claim** (updated):
   - Extension at `https://afiax.africa/fhir/StructureDefinition/kenya-sha-preauthorization`
   - Same structure as the claim submission snapshot, but under the preauth URL
   - Previous preauth extension is replaced; claim submission extension is untouched

3. **AuditEvent**:
   - `type`: `{system: "http://terminology.hl7.org/CodeSystem/audit-event-type", code: "rest"}`
   - `subtype`: `[{code: "operation"}]`
   - `action`: `E`
   - `entity[0]`: Task reference
   - `entity[1]`: Claim reference

## Status flow

```
no credentials → status: "prepared", nextState: "ready-for-sha-preauth-transport"
submitted ok   → status: "submitted", nextState: "awaiting-sha-preauth-decision"
SHA error      → status: "error",     nextState: "retry-or-review-sha-credentials"
```

When `status === "prepared"`, `rawBundle` is returned so the bundle can be submitted manually
or via a connector without re-calling this operation.

## Error conditions

| Condition | HTTP | Description |
|-----------|------|-------------|
| Kenya country pack not active | 400 | `countryPack !== "kenya"` |
| No Claim ID and no `claim` parameter | 400 | Must identify which Claim to pre-authorize |
| Claim not found | 404 | Standard Medplum resource-not-found |
| SHA credentials missing | 200 | Returns `status: "prepared"` with raw bundle; not an error |
| SHA returns non-2xx | 200 | Returns `status: "error"` with SHA response body in `message` |

## Checking pre-authorization status

SHA processes pre-authorization requests asynchronously. To check the decision:

1. Call `Claim/{id}/$check-national-claim-status` — this uses the same SHA status endpoint
   as regular claim status checks. The `bundleId` from the preauth snapshot is used to query SHA.

2. Alternatively wait for the SHA callback — if `kenyaShaClaimsCallbackUrl` is configured,
   SHA will push the decision to `POST /kenya/sha-callback/:projectId`.
